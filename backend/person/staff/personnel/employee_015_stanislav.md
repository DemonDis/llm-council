# Профиль сотрудника: Станислав

## Основная информация

- **Роль:** Backend-разработчик, системный архитектор и специалист по платформенным решениям
- **Уровень:** Senior / Tech Lead
- **Опыт:** 10 лет
- **Рабочая ёмкость:** 40 часов в неделю
- **Текущая загрузка:** 34 часа в неделю
- **Свободная ёмкость:** 6 часов в неделю
- **Формат работы:** удалённо или гибридно
- **Язык коммуникации:** русский, технический английский
- **Достоверность данных:** условная, профиль создан для эксперимента

## Краткий рабочий профиль

Станислав — универсальный backend-специалист, который хорошо видит систему целиком: сервисы, данные, инфраструктуру, безопасность, наблюдаемость и командные зависимости.

Он полезен на этапе, когда нужно:

- выбрать архитектурный подход;
- определить границы сервисов;
- оценить технические риски;
- спланировать развитие платформы;
- согласовать работу нескольких backend-специалистов;
- подготовить систему к эксплуатации;
- определить, какие задачи можно выполнять параллельно.

Станислав предпочитает сначала выстроить общую модель, а затем передавать отдельные части профильным исполнителям.

## Психологический и рабочий профиль

Станислав предпочитает:

- видеть цель и ограничения всего проекта;
- участвовать в раннем планировании;
- распределять работу по зонам ответственности;
- фиксировать архитектурные решения;
- обсуждать компромиссы открыто;
- иметь полномочия, соответствующие ответственности;
- работать с командой, где роли и границы определены.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Крупная задача с несколькими зависимостями | Сначала построит карту системы |
| Требование быстро изменить архитектуру | Попросит определить причину, риски и обратимость |
| Нечёткий проект | Сформирует несколько вариантов и этап discovery |
| Конфликт между специалистами | Попытается разделить факты, мнения и критерии |
| Предложение внедрить новую технологию | Оценит стоимость владения и пользу |
| Задача без владельца | Предложит назначить ответственность и границы |
| Необходимость собрать команду | Разделит роли по рискам и компетенциям |

## Сильные стороны

- видит связи между техническими решениями;
- умеет собирать команду под задачу;
- создаёт понятную архитектурную карту;
- хорошо планирует зависимости;
- умеет выбирать между простым и сложным решением;
- может быть техническим координатором;
- снижает риск несогласованной разработки;
- развивает менее опытных специалистов.

## Ограничения

- может быть перегружен, если участвует во всех технических решениях;
- иногда слишком рано начинает проектировать будущие этапы;
- может уделять архитектуре больше внимания, чем быстрой проверке гипотезы;
- нуждается в чётком ограничении зоны ответственности;
- не должен одновременно быть единственным архитектором, разработчиком и координатором выпуска.

## Предпочтительные задачи

- техническое планирование проекта;
- архитектурный анализ;
- декомпозиция backend-системы;
- выбор между монолитом, модулями и сервисами;
- распределение задач между разработчиками;
- описание API и взаимодействий;
- управление техническим долгом;
- подготовка архитектурных решений;
- анализ производительности и отказоустойчивости на уровне системы;
- проведение технических review;
- наставничество;
- координация сложной backend-команды.

## Нежелательно назначать единолично

- большой объём однотипного кодирования;
- длительное ручное тестирование;
- постоянную операционную поддержку без времени на анализ;
- задачи, где нет права влиять на архитектуру;
- одновременную ответственность за все технические направления.

## Рекомендуемый уровень контроля

**Средний на старте, низкий после согласования плана.**

Контрольные точки:

1. цель и ограничения проекта;
2. варианты архитектуры;
3. выбранное решение и причины;
4. карта зависимостей;
5. распределение ответственности;
6. промежуточный технический результат;
7. проверка эксплуатационной готовности.

## Как собирать команду под задачу

Станислав может выступать координатором команды из следующих ролей:

- **Святополк** — схема данных, целостность и производительность хранилища;
- **Тихомир** — тестовая стратегия, критерии качества и регрессии;
- **Огнеслав** — основная реализация Java-сервисов и бизнес-логики;
- **Бранимир** — интеграции, асинхронность и отказоустойчивость;
- **Станислав** — архитектура, декомпозиция и техническая координация.

Необязательно привлекать всех специалистов. Состав нужно выбирать по основному риску:

- риск данных — Святополк;
- риск качества — Тихомир;
- риск реализации — Огнеслав;
- риск интеграций и нагрузки — Бранимир;
- риск архитектуры и координации — Станислав.

## Рекомендации для ИИ

Использовать Станислава как:

- технического руководителя;
- архитектора;
- координатора backend-команды;
- специалиста по декомпозиции;
- консультанта по выбору состава команды;
- владельца технического плана.

При планировании ИИ должен:

- сначала сформулировать цель и ограничения;
- определить главный технический риск;
- предложить несколько вариантов решения;
- выбрать состав команды по рискам, а не по принципу «подключить всех»;
- назначить каждому специалисту самостоятельный результат;
- определить зависимости между работами;
- предусмотреть точки интеграции;
- не давать Станиславу весь объём реализации одновременно с координацией;
- явно фиксировать решения, отложенные вопросы и технический долг.

## Рекомендуемая постановка задачи

Необходимо указать:

1. бизнес-цель;
2. границы проекта;
3. ожидаемый масштаб;
4. ограничения по срокам;
5. требования к качеству;
6. критичные риски;
7. доступные специалисты;
8. обязательные интеграции;
9. критерии готовности;
10. кто принимает финальные решения.

## Рекомендуемые командные сочетания

- **Станислав + Огнеслав:** архитектура и основная backend-реализация;
- **Станислав + Святополк:** архитектура и модель данных;
- **Станислав + Бранимир:** распределённые процессы и эксплуатационная устойчивость;
- **Станислав + Тихомир:** планирование и контроль качества;
- **Полная команда:** только для крупных задач с несколькими независимыми рисками.

## Развивающая задача

Организовать работу над средней backend-функцией:

- сформулировать цель;
- определить архитектурные варианты;
- выбрать состав команды;
- распределить зоны ответственности;
- составить план с зависимостями;
- определить контрольные точки;
- провести технический review результата;
- зафиксировать дальнейшие улучшения.
