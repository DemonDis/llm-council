## Краткий рабочий профиль

Зореслав — практико-ориентированный Data Scientist, который умеет превращать исследовательскую идею в работающий прототип и доводить модель до использования в прикладном процессе.

Он хорошо работает в условиях неполных требований, если понятна проблема и есть возможность самостоятельно выбрать технический подход. Предпочитает быстро проверить гипотезу на минимальном рабочем решении, а затем улучшать качество, стабильность и масштабируемость.

Зореслав особенно полезен в задачах, где требуется:

- выбрать подходящий тип модели;
- подготовить признаки и обучающую выборку;
- построить прогноз, классификацию или ранжирование;
- сравнить несколько алгоритмов;
- оценить качество модели на новых данных;
- организовать воспроизводимый ML-эксперимент;
- подготовить модель к интеграции;
- настроить мониторинг качества;
- исследовать причины деградации модели;
- найти компромисс между точностью, скоростью и стоимостью.

## Психологический и рабочий профиль

### Предпочтительный способ работы

Зореслав предпочитает:

- получать описание проблемы, а не подробную инструкцию по реализации;
- быстро запускать небольшой технический эксперимент;
- самостоятельно выбирать инструменты и алгоритмы;
- работать с понятным ограничением по времени;
- видеть реальные данные или их репрезентативный срез;
- сравнивать несколько подходов по заранее определённым метрикам;
- разделять прототип и production-решение;
- обсуждать технические риски на конкретных примерах;
- получать короткую обратную связь по ключевым решениям;
- иметь доступ к инженеру при сложной интеграции.

Он плохо работает в режиме постоянного микроменеджмента и при необходимости согласовывать каждую техническую деталь до начала эксперимента.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Практическая задача с доступными данными | Быстро предложит минимальный прототип |
| Общая идея без данных | Спросит, можно ли получить выборку или создать тестовый контур |
| Требование сразу сделать идеальную модель | Предложит разделить работу на baseline, улучшение и production-этап |
| Выбор сложной модели без доказанной пользы | Сначала сравнит её с простым базовым решением |
| Срочная задача с жёстким сроком | Сократит объём и предложит минимально рабочий результат |
| Противоречивые бизнес-требования | Попросит выбрать приоритетную метрику или владельца решения |
| Низкое качество данных | Попытается оценить, можно ли получить полезный baseline |
| Критика модели без конкретных метрик | Попросит определить измеримые критерии |
| Необходимость ручного отчёта | Предложит автоматизировать повторяющуюся часть |
| Запрет на технический эксперимент | Может потерять мотивацию, если не видит способа проверить гипотезу |
| Негативный результат тестирования | Быстро сменит подход, если причина не связана с ошибкой постановки |

## Ограничения и слабые стороны

- может слишком быстро перейти к реализации до полного понимания бизнес-контекста;
- иногда оптимизирует техническую метрику вместо бизнес-результата;
- может недооценить важность пользовательского и операционного процесса;
- не любит длительные согласования и формальные процедуры;
- способен переусложнить решение, если видит интересную техническую возможность;
- не всегда подробно описывает ограничения для нетехнической аудитории;
- нуждается в сильном владельце продукта или аналитике для контроля бизнес-метрик;
- для крупной production-инфраструктуры желательно подключать ML Engineer или Data Engineer.

- работа с недоступными или искусственно ограниченными данными;
- постоянное изменение приоритетов без объяснения;
- необходимость защищать выводы перед аудиторией, которой не определили критерии оценки.

## Базовый план работы с Зореславом

### Этап 1. Проверка применимости ML

- определить проблему;
- проверить наличие данных;
- установить, нужен ли прогноз или классификация;
- определить цену ошибок;
- выбрать критерии успеха.

### Этап 2. Baseline

- подготовить минимальный набор данных;
- реализовать простое правило или базовую модель;
- настроить первоначальную метрику;
- определить технические ограничения;
- зафиксировать исходный результат.

### Этап 3. Исследование улучшений

- проверить качество признаков;
- исследовать альтернативные модели;
- проверить дисбаланс классов;
- исключить утечку данных;
- выполнить кросс-валидацию или временное разбиение;
- сравнить качество, скорость и стоимость.

### Этап 4. Проверка применимости

- оценить модель на независимых данных;
- проверить стабильность по сегментам;
- определить ограничения;
- оценить ошибки первого и второго рода;
- проверить объяснимость результата.

### Этап 5. Подготовка к использованию

- определить способ интеграции;
- подготовить версию модели;
- описать формат входных и выходных данных;
- настроить логирование;
- определить мониторинг качества;
- подготовить план отката.

### Этап 6. Контроль результата

- запустить ограниченную проверку;
- сравнить результат с baseline;
- оценить фактический бизнес-эффект;
- определить необходимость переобучения;
- зафиксировать решение о дальнейшем развитии.

## Как собрать команду под задачу

При выборе команды вокруг Зореслава ИИ должен проверить наличие следующих компетенций:

| Компетенция | Когда необходима |
|---|---|
| Владелец продукта или процесса | Всегда, если модель влияет на бизнес-решение |
| Data Scientist | Для формулировки и проверки аналитической или ML-гипотезы |
| Data Engineer | Если данные нужно регулярно собирать, очищать и обновлять |
| ML Engineer | Если модель должна работать стабильно в промышленной среде |
| Backend-разработчик | Если требуется интеграция с прикладной системой |
| Аналитик | Если нужно оценить эффект, метрики и поведение пользователей |
| Специалист по предметной области | Если ошибки модели имеют высокую стоимость |
| QA или специалист по тестированию | Если модель встроена в критичный рабочий процесс |
| Специалист по безопасности и доступам | Если используются чувствительные или ограниченные данные |

Минимальная команда для исследовательского прототипа:

- Зореслав;
- Любомир или другой аналитик;
- владелец продукта или процесса.

Минимальная команда для production-решения:

- Зореслав;
- Любомир или продуктовый аналитик;
- Data Engineer;
- ML Engineer или Backend-разработчик;
- владелец продукта или процесса.

## Рекомендуемое распределение ответственности

- **Зореслав:** модель, признаки, прототип, техническая оценка, подготовка к интеграции.
- **Любомир:** гипотеза, метрики, дизайн проверки, статистика, оценка эффекта.
- **Data Engineer:** источники, витрины, качество и обновление данных.
- **ML Engineer:** обучение, развёртывание, мониторинг и эксплуатация.
- **Backend-разработчик:** интеграция с прикладной системой.
- **Владелец продукта:** приоритет, бизнес-решение и критерий полезности.
- **Предметный эксперт:** проверка реалистичности признаков и интерпретации.
