# Профиль сотрудника: Тихомир

## Основная информация

- **Роль:** Backend-разработчик, специалист по процессам, тестированию и качеству
- **Уровень:** Middle+
- **Опыт:** 6 лет
- **Рабочая ёмкость:** 40 часов в неделю
- **Текущая загрузка:** 30 часов в неделю
- **Свободная ёмкость:** 10 часов в неделю
- **Формат работы:** удалённо или гибридно
- **Язык коммуникации:** русский, технический английский
- **Достоверность данных:** условная, профиль создан для эксперимента

## Краткий рабочий профиль

Тихомир — последовательный backend-разработчик, который силён в превращении требований в повторяемый процесс разработки и проверки.

Он хорошо работает там, где необходимо:

- формализовать бизнес-правила;
- определить критерии готовности;
- описать позитивные и негативные сценарии;
- построить тестовую стратегию;
- снизить количество ручных ошибок;
- связать разработку, тестирование и выпуск изменений.

Предпочитает понятные правила, прозрачные процессы и постепенное улучшение качества.

## Психологический и рабочий профиль

Тихомир предпочитает:

- задачи с понятным ожидаемым поведением;
- работу через чек-листы, сценарии и критерии;
- предварительное описание рисков;
- последовательное выполнение этапов;
- спокойную коммуникацию без обвинений;
- возможность улучшить процесс после завершения задачи.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Задача с критериями готовности | Быстро составит план проверки |
| «Сделайте как-нибудь, потом проверим» | Попросит описать ожидаемое поведение |
| Срочный выпуск без тестов | Укажет на риски и предложит минимальный набор проверок |
| Повторяющиеся ошибки | Предложит автоматизацию или изменение процесса |
| Конфликт между разработкой и тестированием | Попытается определить объективные критерии |
| Большая задача без этапов | Разделит её на небольшие проверяемые результаты |
| Предложение улучшить CI/CD | Положительно отреагирует при наличии измеримого эффекта |

## Сильные стороны

- переводит требования в проверяемые сценарии;
- умеет находить скрытые условия и исключения;
- снижает количество регрессий;
- создаёт понятный процесс разработки;
- хорошо документирует причины и результаты проверок;
- способен быть связующим звеном между разработчиками, тестировщиками и продуктом;
- не ограничивается проверкой успешного сценария.

## Ограничения

- может воспринимать недостаточно определённую задачу как риск;
- иногда создаёт больше тестов, чем необходимо для простой функции;
- может замедлять выпуск, если не определён минимальный допустимый уровень качества;
- не является специалистом по сложной инфраструктуре;
- нуждается в явном решении о допустимых компромиссах.

## Предпочтительные задачи

- проектирование тестовой стратегии;
- настройка автоматизированных проверок;
- создание unit- и integration-тестов;
- анализ причин повторяющихся дефектов;
- формирование критериев готовности;
- подготовка чек-листов релиза;
- описание бизнес-процессов;
- декомпозиция крупных backend-задач;
- проверка API-контрактов;
- внедрение quality gates в CI/CD;
- анализ регрессий;
- улучшение процесса code review.

## Нежелательно назначать единолично

- задачи, где требуется только быстро написать код без проверки;
- инфраструктурные изменения без DevOps-поддержки;
- проекты с постоянно меняющимися приоритетами;
- политически чувствительные переговоры без владельца продукта;
- задачи, где качество нельзя проверить объективными критериями.

## Рекомендуемый уровень контроля

**Средний.**

Тихомиру нужно согласовать цели и допустимый уровень качества, после чего он может самостоятельно вести процесс.

Контрольные точки:

1. уточнение требований;
2. список рисков и сценариев;
3. тестовая стратегия;
4. результаты автоматических проверок;
5. анализ дефектов после выпуска.

## Рекомендуемая постановка задачи

Необходимо указать:

1. что считается корректным поведением;
2. какие сценарии обязательны;
3. какие ошибки критичны;
4. какой уровень тестирования требуется;
5. что можно отложить;
6. есть ли ограничения по срокам;
7. кто принимает решение о выпуске;
8. какие метрики качества важны.

## Рекомендации для ИИ

Использовать Тихомира как:

- владельца тестовой стратегии;
- специалиста по качеству backend-функций;
- аналитика процессов разработки;
- координатора между разработкой и проверкой;
- автора критериев готовности и релизных чек-листов.

При планировании ИИ должен:

- начинать с описания ожидаемого поведения;
- выделять позитивные, негативные и пограничные сценарии;
- предлагать минимальный и полный уровни тестирования;
- отделять обязательные проверки от желательных;
- учитывать стоимость поддержки тестов;
- просить его провести анализ первопричины повторяющихся дефектов;
- включать его в команду при высоком риске регрессий или сложных бизнес-правилах.
