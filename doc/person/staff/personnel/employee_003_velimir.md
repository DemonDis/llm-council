# Профиль сотрудника: Велимир

## Основная информация

- **Роль:** Frontend-разработчик, AI-интегратор и универсальный технический специалист
- **Уровень:** Middle+
- **Опыт:** 5 лет
- **Рабочая ёмкость:** 40 часов в неделю
- **Текущая загрузка:** 30 часов в неделю
- **Свободная ёмкость:** 10 часов в неделю
- **Формат работы:** удалённо
- **Предпочтительный язык коммуникации:** русский, английский для технической документации и AI-инструментов
- **Достоверность данных:** условная, профиль создан для эксперимента

## Краткий рабочий профиль

Велимир — универсальный frontend-разработчик, который хорошо осваивает новые инструменты и умеет применять ИИ для ускорения анализа, разработки, тестирования и подготовки документации.

Он подходит для задач, где требуется:

- быстро разобраться в новой технологии;
- собрать рабочий прототип;
- интегрировать AI-сервис или автоматизацию;
- проверить техническую гипотезу;
- найти несколько вариантов решения;
- соединить frontend с внешними сервисами;
- ускорить рутинные операции команды;
- работать на стыке разработки, аналитики и экспериментов.

## Психологический и рабочий профиль

### Предпочтительный способ работы

- предпочитает получать проблему, а не заранее выбранное техническое решение;
- любит короткие исследовательские циклы;
- лучше работает, когда можно быстро собрать прототип;
- нормально относится к неполному ТЗ;
- предпочитает самостоятельно выбирать инструменты;
- нуждается в ограничении эксперимента по времени;
- может вести несколько связанных технических направлений;
- плохо переносит длительную однообразную работу без возможности улучшения процесса;
- полезно заранее договориться, когда эксперимент считается завершённым.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Новая техническая гипотеза | Быстро предложит способ проверки |
| AI-инструмент без понятной цели | Начнёт исследовать, но может уйти в сторону |
| Рутинная задача | Выполнит быстрее среднего, но может искать автоматизацию |
| Неполное ТЗ | Начнёт с предположений и прототипа, если нет запрета |
| Требование использовать конкретный старый инструмент | Попросит объяснить ограничения и альтернативы |
| Срочная задача | Быстро включится, если понятен минимальный результат |
| Сложная интеграция | Самостоятельно изучит документацию и предложит план |
| Задача с долгим циклом согласований | Может потерять интерес без промежуточных результатов |
| Противоречивые требования | Попытается проверить несколько вариантов на практике |

## Сильные стороны

- быстро осваивает незнакомые технологии;
- эффективно использует ИИ для разработки и анализа;
- хорошо подходит для технических экспериментов;
- способен создавать рабочие прототипы за короткий срок;
- умеет интегрировать frontend с внешними сервисами;
- может автоматизировать рутинные действия команды;
- быстро находит технические альтернативы;
- полезен в условиях неопределённости;
- может временно закрывать широкий спектр технических задач;
- помогает другим специалистам использовать AI-инструменты.

## Ограничения и слабые стороны

- может начинать реализацию до полного согласования требований;
- иногда выбирает слишком новый или сложный инструмент;
- нуждается в обязательной проверке качества после быстрого прототипирования;
- может недостаточно подробно фиксировать принятые решения;
- иногда недооценивает стоимость сопровождения экспериментального решения;
- не любит монотонные задачи;
- может переключаться между идеями и терять фокус;
- способен переоценить результат AI-инструмента без ручной проверки;
- не должен быть единственным владельцем критически важного решения без code review.

- задачи с критическими рисками и отсутствием code review;
- окончательная оценка безопасности AI-функции;
- задачи, где требуется строго следовать старому процессу без изменений;
- долгий проект без промежуточных результатов;
- подготовка формальной документации без выделенного времени;
- принятие продуктовых решений без участия Борислава и Светозара.

## Рекомендуемый уровень контроля

**Средний или повышенный на этапе завершения.**

На старте Велимиру можно дать высокую автономность. На этапе перехода от прототипа к рабочему решению необходимы:

- проверка архитектуры;
- проверка ограничений AI-инструмента;
- ручная верификация результата;
- code review;
- оценка стоимости поддержки;
- проверка обработки ошибок и нештатных сценариев.

Рекомендуемый формат работы:

1. определить гипотезу;
2. ограничить эксперимент по времени;
3. зафиксировать минимальный результат;
4. собрать прототип;
5. провести проверку;
6. принять решение: удалить, доработать или перевести в production-разработку.

## Мотивация

Велимира мотивируют:

- новые инструменты;
- технические эксперименты;
- возможность автоматизировать работу;
- автономность;
- быстрый видимый результат;
- сложные интеграции;
- возможность влиять на способ разработки;
- обучение других специалистов;
- задачи на стыке frontend и ИИ.

Не мотивируют:

- однообразные задачи без возможности улучшений;
- длительное согласование каждой мелочи;
- запрет на исследование альтернатив;
- отсутствие технического развития;
- работа, где результат невозможно проверить.

## Рекомендуемая постановка задачи

При назначении задачи Велимиру желательно указывать:

1. какую проблему нужно проверить или решить;
2. какой минимальный результат нужен;
3. сколько времени можно потратить на исследование;
4. какие инструменты разрешены или запрещены;
5. что является экспериментом, а что должно попасть в рабочий продукт;
6. какие риски необходимо проверить;
7. как будет оцениваться результат;
8. кто проводит финальную проверку;
9. какие решения нужно задокументировать;
10. что делать, если гипотеза не подтверждается.

## Рекомендации для ИИ

Использовать Велимира как:

- специалиста по AI-инструментам и прикладным интеграциям;
- технического исследователя;
- разработчика прототипов;
- исполнителя задач с высокой неопределённостью;
- автоматизатора рутинных операций;
- специалиста по поиску технических альтернатив;
- временного универсального участника команды.

При планировании с его участием ИИ должен:

- формулировать задачу как проверяемую гипотезу;
- ограничивать время исследования;
- требовать минимально работающий результат;
- отдельно указывать, что является прототипом, а что production-решением;
- предусматривать ручную проверку AI-результатов;
- включать code review и проверку безопасности;
- не давать бесконтрольное право менять архитектуру;
- фиксировать решение по итогам эксперимента;
- не перегружать его большим количеством несвязанных инициатив.

## Рекомендуемые командные сочетания

- **Велимир + Борислав:** технический эксперимент с контролем бизнес-логики и критериев;
- **Велимир + Светозар:** быстрый клиентский прототип и проверка AI-интерфейса;
- **Велимир + Борислав + Светозар:** полноценная проверка продукта от бизнес-гипотезы до пользовательского интерфейса.
