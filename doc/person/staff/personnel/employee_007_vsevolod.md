- **Достоверность данных:** условная, профиль создан для эксперимента
- **Технологическая привязка:** отсутствует

## Краткий рабочий профиль

Всеволод — технически ориентированный системный аналитик. Его сильная сторона — понимание того, как клиентские сценарии превращаются в серверную логику, API-контракты, интеграции и последовательность технических операций.

Он хорошо работает с задачами, где требуется:

- описать взаимодействие сервисов;
- определить API-контракт;
- разобрать серверный сценарий;
- выявить технические зависимости;
- согласовать frontend и backend;
- описать ошибки и пограничные состояния;
- подготовить задачу для backend-разработчика;
- оценить интеграционные риски;
- проверить соответствие реализации согласованному контракту.

Профиль не ориентирован на глубокую работу с базами данных, журналами событий и эксплуатационным мониторингом. Эти направления требуют отдельного специалиста или дополнительной проверки.

## Психологический и рабочий профиль

### Предпочтительный способ работы

Всеволоду желательно выдавать задачу в форме:

- бизнес-цель;
- пользовательский сценарий;
- входные данные;
- ожидаемый результат;
- ограничения;
- участники интеграции;
- требования к ошибкам;
- зависимости;
- критерии готовности.

Он предпочитает:

- короткие, но содержательные обсуждения;
- схемы взаимодействия;
- возможность изучить текущий API или код;
- заранее известные технические ограничения;
- конкретные решения, которые можно проверить;
- работу крупными блоками без частого переключения.

Он плохо относится к постановкам, где требуется «просто сделать интеграцию» без описания данных, источников и ожидаемого поведения при ошибках.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Чёткая задача по API | Быстро уточнит контракт и предложит последовательность действий |
| «Добавить новую функцию» без описания сценария | Попросит описать вход, результат, роли и ошибки |
| Предложение обойти техническое ограничение | Укажет на последствия и предложит альтернативы |
| Срочная интеграция | Сначала определит минимальный рабочий контракт и риски |
| Работа с базой данных | Попросит подключить профильного специалиста |
| Работа с логами и диагностикой | Может помочь с направлением поиска, но не должен быть единственным исполнителем |
| Противоречивые требования frontend и backend | Предложит зафиксировать единый контракт и правила ответственности |
| Хорошо обоснованное изменение | Быстро адаптирует техническое решение |

## Сильные стороны

- хорошо понимает серверную часть продукта;
- умеет проектировать и проверять API-контракты;
- видит последовательность вызовов и зависимости;
- учитывает ошибки, повторные запросы и пограничные состояния;
- умеет переводить бизнес-сценарии в технические требования;
- хорошо взаимодействует с backend-разработчиками;
- способен заранее выявлять интеграционные риски;
- быстро находит несоответствия между документацией и реализацией;
- может участвовать в техническом планировании;
- полезен как связующее звено между аналитикой, frontend и backend.

## Ограничения и слабые стороны

- не является специалистом по проектированию баз данных;
- не должен единолично отвечать за анализ логов;
- не является профильным специалистом по эксплуатации и мониторингу;
- может использовать слишком много технических терминов в общении с бизнесом;
- иногда фокусируется на технической корректности в ущерб скорости согласования;
- может недооценить важность визуального оформления и презентации;
- нуждается в понятном владельце бизнес-решения;
- может спорить с упрощённым решением, если не обозначены ограничения по срокам.

## Рекомендуемый уровень контроля

**Средний или низкий для технически понятных задач.**

На старте необходимо проверить:

1. корректность бизнес-сценария;
2. состав участников интеграции;
3. входные и выходные данные;
4. правила ошибок;
5. требования к совместимости;
6. зоны ответственности других специалистов.

Рекомендуемые контрольные точки:

1. схема взаимодействия;
2. черновой API-контракт;
3. согласование ошибок и пограничных состояний;
4. проверка реализации;
5. интеграционный тест или демонстрация сценария.

## Мотивация

Всеволода мотивируют:

- сложные технические задачи;
- возможность влиять на качество взаимодействия компонентов;
- ясные критерии результата;
- решение реальных проблем, а не формальная работа;
- техническая автономность;
- признание точности и надёжности его решений;
- участие в проектировании общей системы.

Не мотивируют:

- задачи без технических вводных;
- требования «сделать быстро» без описания рисков;
- изменение контракта без уведомления;
- глубокая работа с логами и базами без профильной поддержки;
- обсуждение технических решений на уровне субъективных мнений.

## Рекомендуемая постановка задачи

При назначении задачи Всеволоду желательно указать:

1. какую бизнес-проблему решаем;
2. какой пользовательский сценарий поддерживаем;
3. кто вызывает систему;
4. какие данные поступают на вход;
5. какой результат должен быть возвращён;
6. какие ошибки возможны;
7. какие компоненты участвуют;
8. какие ограничения уже известны;
9. какие изменения недопустимы;
10. кто отвечает за проверку базы, логов и эксплуатации.

При планировании с его участием ИИ должен:

- сначала сформулировать бизнес-сценарий;
- построить последовательность взаимодействия компонентов;
- описать входные и выходные данные;
- отдельно перечислить ошибки и пограничные случаи;
- проверить необходимость специалиста по базе данных;
- проверить необходимость специалиста по логам и эксплуатации;
- не назначать ему задачи, где большая часть работы связана с базой или журналами;
- предложить минимальный технический контракт для первой версии;
- разделить обязательные и последующие улучшения.

## Как собрать команду с участием Всеволода

Для задачи с backend или интеграцией рекомендуется:

1. **Бизнес-процессный аналитик** определяет цель и правила процесса.
2. **Яромир** оформляет сценарии, требования и критерии приёмки.
3. **Всеволод** проектирует API, взаимодействия и технические ограничения.
4. Backend-разработчик реализует решение.
5. Специалист по данным или эксплуатации подключается к задачам базы, логов и мониторинга.
6. Тестировщик проверяет основные и ошибочные сценарии.

Всеволоду лучше передавать ответственность за:

- техническую декомпозицию;
- API-контракт;
- интеграционные зависимости;
- описание ошибок;
- проверку согласованности технической реализации.

- описать обязательные разделы;

- описать типовые ошибки;
- добавить правила версионирования;
- предусмотреть повторные запросы и тайм-ауты;
- подготовить пример интеграционной схемы;
- проверить стандарт на двух разных задачах.
