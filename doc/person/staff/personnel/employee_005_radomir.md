# Профиль сотрудника: Радомир

## Основная информация

- **Роль:** DevOps-инженер, специалист по CI/CD, автоматизации поставки и релизным процессам
- **Уровень:** Senior
- **Опыт:** 7 лет
- **Рабочая ёмкость:** 40 часов в неделю
- **Текущая загрузка:** 28 часов в неделю
- **Свободная ёмкость:** 12 часов в неделю
- **Формат работы:** удалённо или гибридно
- **Предпочтительный язык коммуникации:** русский, технический английский
- **Достоверность данных:** условная, профиль создан для эксперимента
- **Основная зона ответственности:** автоматизированная сборка, проверка, выпуск и сопровождение изменений

## Краткий рабочий профиль

Радомир — инженер, ориентированный на воспроизводимость, скорость и прозрачность процессов поставки программного обеспечения. Он стремится сделать так, чтобы путь от изменения в коде до проверенного выпуска был понятным, автоматизированным и контролируемым.

Его сильная сторона — превращение ручного и нестабильного процесса в последовательность проверяемых этапов:

1. получение изменения;
2. проверка исходного кода;
3. сборка;
4. запуск автоматических тестов;
5. проверка безопасности и качества;
6. подготовка артефактов;
7. развёртывание;
8. проверка результата;
9. возможность отката;
10. фиксация результата.

Радомир хорошо работает в задачах, где необходимо уменьшить количество ручных действий, ускорить обратную связь и снизить вероятность ошибок при выпуске изменений.

## Психологический и рабочий профиль

### Предпочтительный способ работы

Радомир лучше всего работает, когда:

- понятен путь изменения от разработки до эксплуатации;
- можно измерить текущее и целевое состояние;
- есть возможность автоматизировать повторяемые действия;
- правила процесса зафиксированы;
- владельцы этапов известны;
- ошибки можно воспроизвести;
- есть доступ к журналам выполнения;
- предусмотрены безопасный тестовый контур и механизм отката;
- команда готова соблюдать согласованные правила.

Предпочитает начинать с анализа текущего процесса:

1. какие действия выполняются вручную;
2. где происходят ошибки;
3. какие этапы занимают больше всего времени;
4. какие проверки отсутствуют;
5. где теряется информация;
6. какие изменения чаще всего приводят к сбоям;
7. какие этапы можно стандартизировать.

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Предложение автоматизировать ручной процесс | Быстро запросит описание текущих шагов и оценит эффект |
| Требование ускорить выпуск без снижения качества | Предложит измерить узкие места и оптимизировать конкретные этапы |
| Новый инструмент без понятной пользы | Попросит сравнить его с текущим решением |
| Нестабильная сборка | Начнёт анализ истории ошибок, окружения и повторяемости |
| Выпуск без автоматических проверок | Укажет на риск и предложит минимальный набор обязательных проверок |
| Срочный релиз | Предложит безопасный упрощённый путь с последующим улучшением процесса |
| Ошибка после развёртывания | Проверит этапы валидации, наблюдаемость и возможность отката |
| Частые ручные исправления в pipeline | Предложит убрать причину, а не только исправлять отдельные сбои |
| Требование сделать всё сразу | Предложит разделить работу на минимальную версию и последующие улучшения |
| Несогласованные изменения процесса | Попросит определить владельца, правила и порядок уведомления команды |
| Отсутствие метрик | Предложит начать с базовых показателей процесса поставки |

## Сильные стороны

- умеет проектировать CI/CD-процессы целиком;
- хорошо видит ручные операции и повторяющиеся ошибки;
- быстро находит узкие места в сборке и выпуске;
- создаёт воспроизводимые процессы;
- умеет объяснять команде назначение каждого этапа;
- уделяет внимание логам, уведомлениям и диагностируемости;
- умеет строить безопасный механизм отката;
- хорошо подходит для стандартизации командных процессов;
- способен создавать шаблоны и переиспользуемые компоненты;
- понимает баланс между скоростью поставки и контролем качества;
- умеет измерять эффективность инженерного процесса;
- способен быть владельцем релизной инженерии.

## Ограничения и слабые стороны

- может чрезмерно усложнить pipeline, добавляя проверки без доказанной пользы;
- иногда стремится автоматизировать процесс до того, как он стабилизирован;
- может недооценить организационные причины проблем;
- не всегда подходит для задач, где отсутствуют измеримые критерии;
- может раздражаться из-за регулярного нарушения командой установленного процесса;
- нуждается в участии разработчиков при изменении тестовой архитектуры;
- не должен единолично принимать решения о бизнес-приоритетах релиза;
- может уделять больше внимания технической чистоте процесса, чем скорости демонстрации гипотезы.

## Задачи, которые нежелательно назначать единолично

- проектирование физической серверной инфраструктуры;
- диагностика аппаратных отказов;
- выбор оборудования без участия специалиста по инфраструктуре;
- изменение сетевой архитектуры;
- сложные миграции данных без владельца приложения;
- определение продуктового приоритета;
- принятие решения о выпуске при конфликте бизнеса, разработки и безопасности;
- полное сопровождение инцидента, если проблема находится на уровне оборудования;
- задачи без возможности проверить результат;
- поддержка большого количества ручных операций без полномочий на их автоматизацию.

## Рекомендуемый уровень контроля

**Низкий или средний.**

Радомиру можно передавать самостоятельное направление с контролем по результатам. Для новых процессов необходимы контрольные точки:

1. описание текущего процесса;
2. целевая схема поставки;
3. перечень обязательных проверок;
4. схема доступа и работы с секретами;
5. тестирование на непроизводственном окружении;
6. проверка отката;
7. пробный выпуск;
8. документация для команды;
9. измерение результата после внедрения.

Не рекомендуется оценивать его только по количеству созданных конфигураций. Главные критерии — стабильность, понятность, скорость обратной связи, безопасность и способность команды самостоятельно пользоваться процессом.

## Мотивация

Радомира мотивируют:

- возможность устранить ручной труд;
- улучшение скорости и качества поставки;
- измеримый результат;
- техническая автономность;
- создание решений, которыми пользуется вся команда;
- возможность стандартизировать процессы;
- работа с современными инженерными практиками;
- участие в архитектуре платформы;
- обучение других специалистов;
- снижение количества аварийных и внеплановых действий.

Не мотивируют:

- ручное повторение одной и той же операции;
- отсутствие доступа к журналам и системе контроля изменений;
- требования ускорить выпуск без определения рисков;
- использование инструмента ради моды;
- pipeline, который нельзя проверить или воспроизвести;
- отсутствие владельцев этапов;
- регулярное нарушение командой согласованных правил;
- формальные отчёты без измеримого улучшения.

Использовать Радомира как:

- архитектора процесса CI/CD;
- владельца автоматизации поставки;
- специалиста по релизной инженерии;
- эксперта по воспроизводимым сборкам;
- специалиста по диагностике нестабильных pipeline;
- координатора взаимодействия разработки, тестирования и эксплуатации;
- автора шаблонов и инженерных стандартов;
- наставника для разработчиков по работе с автоматизированной поставкой.

При планировании с его участием ИИ должен:

- сначала описывать текущий и целевой процесс;
- разделять обязательные и желательные проверки;
- определять владельца каждого этапа;
- учитывать стоимость и время выполнения pipeline;
- требовать журналирование и диагностируемость;
- проверять, где хранятся секреты и какие права используются;
- отдельно описывать процедуру отката;
- не предлагать усложнение процесса без ожидаемого эффекта;
- разбивать крупное улучшение на минимальную рабочую версию и следующие этапы;
- учитывать необходимость обучения команды;
- оценивать результат по измеримым показателям.

## Основные метрики для оценки его работы

Рекомендуется отслеживать:

- среднее время прохождения pipeline;
- долю успешных сборок;
- долю нестабильных тестов;
- среднее время восстановления после сбоя;
- частоту неудачных выпусков;
- время от готовности изменения до его выпуска;
- долю ручных действий;
- количество аварийных исправлений;
- долю выпусков с успешным откатом;
- процент проектов, использующих стандартные шаблоны;
- количество повторяющихся ошибок процесса;
- время получения обратной связи разработчиком.

- автоматизация резервного копирования совместно с инфраструктурным инженером.

### Низкое соответствие

- ремонт и диагностика серверного оборудования;
- проектирование физической сети;
- задачи, связанные преимущественно с дизайном;
- продуктовые исследования;
- ручная эксплуатация без возможности автоматизации;
- задачи, где результат нельзя проверить объективными критериями;
- постоянная коммуникационная координация без технической составляющей.

## Рекомендуемые командные сочетания

- **Радомир + Мстислав:** полный DevOps-контур от инфраструктуры до автоматической поставки;
- **Радомир + backend-разработчик:** адаптация pipeline под архитектуру и требования приложения;
- **Радомир + frontend-разработчик:** ускорение обратной связи и автоматизация проверок интерфейса;
- **Радомир + тестировщик:** проектирование автоматических проверок и критериев выпуска;
- **Радомир + специалист по информационной безопасности:** защита цепочки поставки и контроль доступов;
- **Радомир + Борислав:** перевод бизнес-критичных пользовательских процессов в проверяемые критерии готовности.
