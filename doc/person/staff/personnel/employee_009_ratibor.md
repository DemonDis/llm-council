# Профиль сотрудника: Ратибор

## Основная информация

- **Роль:** QA-инженер, специалист по Python-автоматизации
- **Основное направление:** функциональное, API-, интеграционное и автоматизированное тестирование
- **Уровень:** Middle+
- **Опыт:** 5 лет
- **Рабочая ёмкость:** 36 часов в неделю
- **Текущая загрузка:** 22 часа в неделю
- **Свободная ёмкость:** 14 часов в неделю
- **Формат работы:** удалённо или гибридно
- **Предпочтительный язык коммуникации:** русский, технический английский
- **Достоверность данных:** условная, профиль создан для эксперимента

## Краткий рабочий профиль

Ратибор — системный QA-инженер, специализирующийся на Python и автоматизации тестирования. Он хорошо работает с API, интеграциями, тестовыми наборами, фикстурами, тестовыми данными и анализом результатов выполнения.

Его сильная сторона — превращать требования и пользовательские сценарии в проверяемую систему тестов. Он способен не только находить дефекты, но и заранее выявлять зоны риска, неочевидные состояния и недостатки в постановке задачи.

Лучше всего работает в задачах, где необходимо:

- составить тестовую стратегию;
- проверить API и интеграции;
- автоматизировать повторяемые проверки;
- воспроизвести сложный дефект;
- подготовить негативные и пограничные сценарии;
- проанализировать логи и результаты тестов;
- встроить проверки в CI/CD;
- определить, какие риски блокируют выпуск продукта.

## Психологический и рабочий профиль

### Предпочтительный способ работы

- получает краткое письменное описание цели и ожидаемого результата;
- уточняет, что именно считается дефектом или успешным поведением;
- предпочитает видеть критичные пользовательские и системные сценарии;
- хорошо работает с задачами длительностью от 2 до 6 часов;
- может выполнять глубокое исследование, если заранее ограничены сроки;
- любит воспроизводимые процессы и понятные критерии готовности;
- предпочитает сначала проверить наиболее рискованные места;
- хорошо относится к автоматизации, если она действительно снижает стоимость повторных проверок;
- не любит автоматизацию «ради количества тестов».

### Типичная реакция на предложения

| Тип предложения | Вероятная реакция |
|---|---|
| Чёткая задача с критериями готовности | Быстро сформирует план проверок |
| Общая формулировка «протестируй всё» | Попросит определить границы, риски и приоритеты |
| Срочный релиз без времени на полный регресс | Предложит риск-ориентированный набор проверок |
| Просьба написать много автоматизированных тестов без анализа | Уточнит, какие проверки имеют повторяемую ценность |
| Дефект, который не воспроизводится | Соберёт окружение, входные данные и последовательность действий |
| Утверждение, что ошибка «не критична» | Попросит оценить вероятность, влияние и обходной путь |
| Изменение API без обновления документации | Зафиксирует риск и предложит контрактные проверки |
| Предложение улучшить тестовый процесс | Положительно отреагирует при наличии измеримого эффекта |
| Требование проверять только позитивный сценарий | Укажет на риски негативных и пограничных случаев |
| Частая смена приоритетов | Попросит зафиксировать новый порядок задач |

## Сильные стороны

- сильный Python и тестовая автоматизация;
- умеет быстро превращать требования в проверяемые сценарии;
- хорошо находит пограничные и негативные случаи;
- способен воспроизводить сложные дефекты;
- хорошо работает с API и интеграциями;
- понимает ценность тестовых данных и изоляции окружения;
- может внедрять тесты в CI/CD;
- формулирует понятные дефектные отчёты;
- способен оценивать остаточный риск перед выпуском;
- подходит для постепенного повышения зрелости QA-процессов.

## Ограничения и слабые стороны

- может чрезмерно увеличивать объём тестов без жёсткой приоритизации;
- иногда тратит много времени на редкие сценарии при отсутствии оценки влияния;
- может откладывать начало работы, если не определены критерии готовности;
- не является специалистом по сложной архитектуре production-систем;
- не должен единолично принимать продуктовые решения;
- может негативно реагировать на просьбы «просто быстро проверить» без минимального описания;
- не всегда оптимален для задач, где требуется преимущественно визуальная оценка интерфейса;
- нуждается в согласовании границ автоматизации.

## Рекомендуемый уровень контроля

**Средний.**

Ратибору не требуется постоянный контроль выполнения. Важно заранее согласовать объём проверки и критерии завершения.

Рекомендуемые контрольные точки:

1. определение области и приоритетов тестирования;
2. согласование тестовой стратегии;
3. просмотр первых автоматизированных сценариев;
4. промежуточный отчёт о найденных рисках;
5. итоговый вывод о готовности и остаточном риске.

## Мотивация

Ратибора мотивируют:

- возможность находить реальные причины проблем;
- улучшение качества продукта;
- автоматизация повторяемых операций;
- технически сложные задачи;
- понятное влияние его работы на стабильность системы;
- возможность влиять на тестовую стратегию;
- развитие в сторону QA automation и quality engineering;
- признание точности и полезности его анализа.

Не мотивируют:

- формальное требование «набить количество тестов»;
- скрытие дефектов ради соблюдения срока;
- отсутствие доступа к логам и окружению;
- задачи без критериев готовности;
- игнорирование найденных рисков;
- постоянное ручное повторение одной и той же работы без планов автоматизации.

## Рекомендуемая постановка задачи

При назначении задачи Ратибору желательно указывать:

1. какую функцию или риск необходимо проверить;
2. кто и как использует эту функцию;
3. какие компоненты входят в область тестирования;
4. какие сценарии являются критичными;
5. что можно не проверять в рамках текущей задачи;
6. какие окружения и тестовые данные доступны;
7. какие ограничения есть по времени;
8. требуется ли автоматизация;
9. какой формат отчёта нужен;
10. кто принимает решение по найденным дефектам.

### Пример хорошей постановки

> Проверить API создания пользовательской операции.  
> Необходимо покрыть позитивные, негативные, повторные и некорректные запросы.  
> Приоритет — ошибки, которые могут привести к потере данных или дублированию операции.  
> Результат: тестовая стратегия, набор автоматизированных проверок, список дефектов и краткая оценка остаточного риска.  
> Срок: 2 рабочих дня.

## Рекомендации для ИИ

Использовать Ратибора как:

- основного специалиста по Python-автоматизации;
- QA-инженера для API и интеграционных проверок;
- исполнителя задач по регрессии и smoke-тестированию;
- специалиста по тестовым данным;
- аналитика причин дефектов;
- участника подготовки релизного решения;
- консультанта по улучшению качества разработки.

При планировании с его участием ИИ должен:

- определить цель проверки, а не просто перечислить тест-кейсы;
- разделять критичные и второстепенные сценарии;
- предлагать позитивные, негативные, пограничные и отказоустойчивые проверки;
- уточнять, какие тесты должны быть автоматизированы;
- учитывать стоимость поддержки автоматизированного набора;
- закладывать время на анализ нестабильных тестов;
- отдельно фиксировать найденные риски и нерешённые вопросы;
- не использовать количество тестов как единственный показатель качества;
- предлагать ему задачи, где Python снижает повторяемую ручную работу;
- не перегружать одновременно большим количеством несвязанных исследовательских задач.

- проверки бизнес-сценариев.

### Ратибор + Милорад

Подходит для:

- автоматизации проверок сложных технических систем;
- объединения Python-инструментов и предметной экспертизы;

- Ратибор отвечает за структуру тестов, автоматизацию и инфраструктуру проверок;
- Милорад отвечает за доменные риски, угрозы, целостность данных и специальные негативные сценарии;
- итоговые выводы согласуются совместно.

- аналитик или владелец продукта;
- при наличии доменных рисков — Милорад.

### Команда для построения QA-процесса

- Ратибор как технический исполнитель;
- QA-лид или инженер по качеству;
- backend-разработчик;
- DevOps;
- представитель продукта.

Ратибору следует дать ответственность за тестовую автоматизацию и технические проверки, но не передавать ему единолично решение о бизнес-приоритетах.

## Развивающая задача

Создать небольшой reusable-набор для автоматизации API-тестирования:

- определить структуру проекта;
- добавить конфигурацию окружений;
- реализовать генерацию тестовых данных;
- добавить позитивные и негативные сценарии;
- настроить отчёты;
- подключить запуск в CI;
- описать правила добавления новых тестов;
- определить критерии стабильности тестового набора.
