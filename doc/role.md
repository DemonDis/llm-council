## Что это за программа

Это приложение **LLM Council** — «совет» из языковых моделей или виртуальных личностей. Пользователь задаёт вопрос, после чего система:

1. собирает несколько независимых ответов;
2. просит участников оценить эти ответы;
3. подсчитывает общий рейтинг;
4. передаёт все материалы отдельной модели-председателю;
5. председатель формирует итоговый ответ.

В интерфейсе результаты показываются в виде трёх этапов.

---

# 1. Общая схема работы

Приложение состоит из двух частей:

- **Frontend** на React — интерфейс, чаты, настройки, переключение режимов;
- **Backend** на FastAPI — запросы к моделям OpenRouter, проведение трёх этапов и хранение разговоров в JSON-файлах.

После отправки вопроса frontend вызывает:

```text
POST /api/conversations/{id}/message/stream
```

Backend начинает отправлять события через SSE — Server-Sent Events. Поэтому в интерфейсе постепенно появляются:

- ответы ролей;
- их оценки;
- итоговый ответ председателя.

Каждое сообщение пользователя и полный ответ совета сохраняются в файле разговора.

---

# 2. Два режима работы

## Режим «Ролевой мозговой штурм»

Это режим по умолчанию в интерфейсе.

В файле `backend/roles.json` описаны виртуальные личности. Сейчас там 12 ролей:

- Мечтатель;
- Перфекционист;
- Консерватор;
- Циничный Гений;
- Перестраховщик;
- Конформист;
- Манипулятор;
- Практик;
- Голос Клиента;
- Аналитик;
- Риск-менеджер;
- Дипломат.

Все эти личности реализуются **одной и той же моделью**, указанной в настройке:

```env
ROLEPLAY_MODEL=...
```

То есть это не 12 разных нейросетей. Для каждой роли создаётся отдельный запрос к одной модели, но с разным описанием характера и поведения.

Например, запрос к модели выглядит примерно так:

```text
System Instruction:
Ты — Практик...
Мыслишь бюджетами, сроками и ресурсами...

User Query:
Стоит ли нам запускать новую функцию?
```

В коде инструкция роли передаётся как обычное пользовательское сообщение с текстом `System Instruction`, а не как настоящее сообщение с ролью `system`. Это сделано для совместимости с некоторыми моделями.

---

## Режим «Битва моделей»

В этом режиме используются разные модели из:

```env
COUNCIL_MODELS=model1,model2,model3
```

Каждая модель получает один и тот же вопрос и самостоятельно отвечает на него.

Например:

```text
DeepSeek отвечает на вопрос
Qwen отвечает на вопрос
Ещё одна модель отвечает на вопрос
```

Затем эти модели оценивают ответы друг друга, а председатель формирует общий вывод.

Здесь уже различия между участниками обусловлены не ролями, а архитектурой, обучением и стилем разных моделей.

# 3. Этап 1 — индивидуальные ответы

## В ролевом режиме

Backend перебирает все роли из `roles.json`.

Для каждой роли он отправляет:

- описание личности;
- исходный вопрос пользователя.

Например:

### Перфекционист

Будет искать:

- логические ошибки;
- неучтённые детали;
- риски реализации;
- слабые места плана.

### Консерватор

Будет вспоминать:

- похожие прошлые провалы;
- риски нового решения;
- возможные поломки;
- недостаток проверенных данных.

### Практик

Переведёт идею в:

- сроки;
- бюджет;
- количество ресурсов;
- трудозатраты;
- технические ограничения.

### Голос Клиента

Спросит:

- какую проблему это решает;
- зачем это пользователю;
- будет ли удобно этим пользоваться;
- сколько это будет стоить человеку.

### Аналитик

Потребует:

- метрики;
- источники данных;
- проверяемую гипотезу;
- критерии успеха или провала.

### Дипломат

Попробует найти компромисс между позициями других участников.

В результате появляется массив примерно такого вида:

```json
[
  {
    "model": "Deepseek/...",
    "role": "Мечтатель",
    "response": "..."
  },
  {
    "model": "Deepseek/...",
    "role": "Практик",
    "response": "..."
  }
]
```

## В режиме моделей

Вместо ролей появляются ответы разных моделей:

```json
[
  {
    "model": "Deepseek/...",
    "response": "..."
  },
  {
    "model": "Qwen/...",
    "response": "..."
  }
]
```

Важно: предыдущая история разговора в этот этап не передаётся. Каждый новый вопрос обрабатывается в основном отдельно. История сохраняется для отображения, но модели получают текущий вопрос и результаты текущего раунда.

# 4. Этап 2 — как личности оценивают друг друга

Это основная часть системы.

Допустим, на первом этапе получились три ответа:

```text
Ответ Мечтателя
Ответ Практика
Ответ Аналитика
```

Перед оцениванием backend скрывает настоящие имена и заменяет их анонимными метками:

```text
Response A
Response B
Response C
```

Например:

```text
Response A:
Предлагаю выйти на новый рынок...

Response B:
Разработка займёт около шести месяцев...

Response C:
Сначала нужно проверить спрос на небольшой выборке...
```

Затем каждой роли отправляется один и тот же набор ответов и инструкция:

1. оценить каждый ответ;
2. объяснить его сильные и слабые стороны;
3. в конце составить рейтинг от лучшего к худшему.

Модель должна закончить ответ строго в таком формате:

```text
FINAL RANKING:
1. Response C
2. Response B
3. Response A
```

## Как влияет характер роли

Все роли видят одинаковые ответы, но анализируют их через разные инструкции.

### Мечтатель

С большей вероятностью поддержит:

- масштабные идеи;
- новые рынки;
- долгосрочные возможности.

Если другой ответ подтверждён цифрами или успешным примером, Мечтатель должен признать его ценность.

### Перфекционист

Будет искать ошибки и недостающие детали:

```text
Это не сработает, потому что не учтены...
```

Но при наличии сильных логических аргументов способен изменить мнение.

### Консерватор

Сначала отнесётся к новому решению подозрительно:

```text
Мы уже видели подобный подход — он создаёт риск...
```

Его можно убедить успешным прецедентом или данными.

### Циничный Гений

Оценивает прежде всего:

- техническую архитектуру;
- наличие технических дыр;
- элегантность решения;
- реалистичность реализации.

Может использовать сарказм, но промпт запрещает прямые оскорбления людей.

### Перестраховщик

Будет обращать внимание на:

- фиксацию договорённостей;
- распределение ответственности;
- наличие документации;
- формальные процедуры.

### Манипулятор

Может оценивать, кому лучше передать задачу, и пытаться представить дополнительную работу как «точку роста».

### Практик

Будет смотреть на:

- дедлайны;
- ресурсы;
- стоимость;
- техническую сложность;
- возможность реально выполнить план.

### Голос Клиента

Будет оценивать ответы с точки зрения пользователя:

```text
Решает ли это реальную проблему?
Поймёт ли человек, как этим пользоваться?
```

### Аналитик

Скорее всего понизит рейтинг ответа без:

- цифр;
- проверяемой гипотезы;
- способа измерить результат.

### Риск-менеджер

Проверит:

- юридические риски;
- финансовые риски;
- репутационные риски;
- регуляторные ограничения.

### Дипломат

Попытается увидеть полезные части разных ответов и найти сбалансированный вариант.

# 5. Как из рейтингов получается общий результат

Каждый участник отдаёт свой порядок ответов.

Например:

```text
Мечтатель:
1. Response A
2. Response C
3. Response B

Практик:
1. Response C
2. Response B
3. Response A

Аналитик:
1. Response C
2. Response A
3. Response B
```

Backend переводит позиции в числа:

- первое место = 1;
- второе место = 2;
- третье место = 3.

Затем считается средняя позиция каждого ответа.

Например:

```text
Response A: (1 + 3 + 2) / 3 = 2.00
Response B: (3 + 2 + 3) / 3 = 2.67
Response C: (2 + 1 + 1) / 3 = 1.33
```

Итог:

```text
1. Response C — среднее место 1.33
2. Response A — среднее место 2.00
3. Response B — среднее место 2.67
```

В интерфейсе анонимные обозначения заменяются обратно на имена ролей или моделей. Поэтому пользователь видит, например:

```text
1. Аналитик
2. Практик
3. Мечтатель
```

При этом модель-оценщик во время самой оценки видит только `Response A`, `Response B` и так далее. Это снижает влияние авторитета имени конкретной модели или роли.

# 6. Этап 3 — председатель

После завершения рейтингов отдельная модель:

```env
CHAIRMAN_MODEL=...
```

получает:

- исходный вопрос;
- все ответы первого этапа;
- все подробные оценки;
- итоговые рейтинги;
- сведения о согласии и разногласиях.

Председатель должен не просто выбрать победителя, а синтезировать итоговый ответ.

В ролевом режиме ему предлагается учитывать:

- идеи визионеров;
- риски скептиков;
- практические шаги исполнителей;
- мнение клиента;
- фактические данные;
- взаимные оценки.

То есть результат — это не дословный ответ одной личности, а попытка собрать из всех ответов единое решение.

---

# 7. Что именно означает «личности оценивают друг друга»

Здесь нет полноценного диалога в стиле:

```text
Практик ответил Мечтателю,
Мечтатель возразил Практику,
Аналитик вмешался в спор.
```

На самом деле процесс такой:

```text
1. Все роли независимо отвечают на вопрос.
2. Все роли получают общий набор анонимизированных ответов.
3. Каждая роль независимо пишет критику и рейтинг.
4. Председатель анализирует весь массив результатов.
```

То есть это **параллельное независимое оценивание**, а не последовательная дискуссия с памятью и репликами.

Роль не обладает настоящей самостоятельной личностью или долговременной памятью. «Личность» задаётся текстом системной инструкции в каждом отдельном запросе.

# 8. Важные особенности реализации

## Ответ можно оценивать самому

Несмотря на формулировки вроде «оцените ответы остальных», код не исключает собственный ответ роли из списка.

Каждая роль получает все ответы:

```text
Response A
Response B
Response C
...
```

Поэтому роль потенциально оценивает и собственный ответ, хотя из-за анонимизации не знает, какой именно ответ принадлежит ей.

То же относится к режиму «Битва моделей»: модель также получает полный список ответов, включая потенциально свой.

## `roles.json` — активный файл ролей

Файл `roles-all.json` в текущем коде не используется. Загружается именно:

```text
backend/roles.json
```

Если файл не найден или повреждён, используются резервные роли из `config.py`.

## Рейтинг является порядковым

Система не просит ставить оценки по шкале от 1 до 10. Участники только располагают ответы по местам:

```text
1-е место
2-е место
3-е место
```

Поэтому общий результат отражает среднюю позицию, а не абсолютное качество.

## Невалидный рейтинг может потеряться

Backend ищет в ответе модели секцию:

```text
FINAL RANKING:
```

и строки формата:

```text
1. Response A
```

Если модель нарушит формат, часть рейтинга может не распознаться и не попасть в агрегированный результат.

## В потоковом режиме ответы приходят постепенно

Для ролевого режима frontend получает отдельные события:

```text
stage1_role_start
stage1_chunk
stage1_complete
stage2_role_start
stage2_chunk
stage2_complete
stage3_chunk
stage3_complete
```

Поэтому пользователь видит, как роль «печатает» ответ, а не ждёт окончания всего процесса.

---

## Кратко в одной схеме

```text
Пользовательский вопрос
          ↓
Этап 1: независимые ответы ролей или моделей
          ↓
Ответы переименовываются в Response A, B, C...
          ↓
Этап 2: каждая роль критикует и ранжирует все ответы
          ↓
Подсчёт средних позиций
          ↓
Этап 3: председатель получает все материалы
          ↓
Итоговый коллективный ответ
```

Главная идея программы: не доверять одному ответу, а сравнить несколько точек зрения — стратегическую, техническую, клиентскую, аналитическую, юридическую и практическую — после чего объединить их в один вывод.









Нет, **21 анкета сотрудников — это не много для ИИ**, если правильно организовать информацию. Проблема обычно не в количестве сотрудников, а в том, что в каждый запрос загружается слишком много лишних подробностей.

## Оптимальный подход

Не нужно каждый раз передавать ИИ все 21 полных профиля. Лучше использовать три уровня данных.

### 1. Краткая карточка сотрудника

Используется для первичного поиска подходящих людей.

```md
# employee_001 — Анна

- Роль: Backend-разработчик, Middle
- Доступно: 8 часов в неделю
- Python: 5/5
- FastAPI: 5/5
- PostgreSQL: 4/5
- Docker: 3/5
- Коммуникация: 4/5
- Ответственность: 5/5
- Работа с неопределённостью: 3/5
- Презентации: 2/5
- Лучше всего: API, backend, базы данных, тестирование
- Не рекомендуется: публичные презентации, переговоры с клиентом
- Предпочитает: письменные задачи, минимум встреч, понятные критерии
- Уровень контроля: средний
```

Такая карточка может занимать примерно **100–200 слов**.

Для 21 сотрудника это будет всего около **2 000–4 000 слов**, что вполне комфортно.

---

### 2. Матрица команды

Дополнительно можно создать общий файл:

```md
# Матрица компетенций команды

| Сотрудник | Роль | Python | FastAPI | PostgreSQL | Docker | QA | Коммуникация | Презентации | Свободные часы |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Анна | Backend | 5 | 5 | 4 | 3 | 4 | 4 | 2 | 8 |
| Иван | Frontend | 2 | 1 | 2 | 3 | 3 | 4 | 4 | 12 |
| Олег | DevOps | 2 | 2 | 3 | 5 | 3 | 3 | 3 | 6 |
```

Эта таблица позволяет ИИ быстро ответить:

- кто знает нужную технологию;
- у кого есть свободное время;
- кто может быть резервом;
- кто подходит для коммуникации с клиентом;
- где в команде есть пробелы.

---

### 3. Полный профиль

Полную анкету нужно использовать только после предварительного отбора.

Например:

1. ИИ анализирует новую задачу по кратким карточкам всех 21 сотрудников.
2. Выбирает 3–5 наиболее подходящих кандидатов.
3. Подробно изучает полные профили только этих сотрудников.
4. Формирует состав команды и план работы.

Это лучше, чем постоянно отправлять все 21 подробных анкеты.

# Какой объём анкеты оптимален

## Для постоянного использования

На одного сотрудника достаточно:

- роль и уровень;
- 5–10 ключевых hard skills;
- 5–8 soft skills;
- сильные стороны;
- ограничения;
- рабочие предпочтения;
- подходящие и нежелательные задачи;
- доступная ёмкость;
- уровень самостоятельности;
- дата обновления профиля.

Оптимальный размер:

```text
150–400 слов на сотрудника
```

Для 21 сотрудника:

```text
примерно 3 000–8 000 слов
```

Это нормальный объём для работы ИИ.

## Когда информации становится слишком много

Если каждый профиль занимает 1 000–2 000 слов, то 21 анкета может превратиться в большой документ на 20 000–40 000 слов. Технически ИИ может с ним работать, но:

- возрастает стоимость обработки;
- ответы становятся медленнее;
- повышается риск пропустить важную деталь;
- ИИ может сильнее ориентироваться на объём текста, а не на реальные критерии;
- сложнее поддерживать актуальность данных.

# Как должен работать ИИ

## Этап 1. Первичный отбор

ИИ получает:

- описание задачи;
- матрицу компетенций;
- краткие карточки сотрудников.

Он отбирает людей по фильтрам:

```text
1. Есть ли обязательный hard skill?
2. Есть ли свободные часы?
3. Подходит ли уровень самостоятельности?
4. Может ли сотрудник работать в нужном темпе?
5. Требуются ли коммуникации, презентации или переговоры?
```

## Этап 2. Подробный анализ

После этого ИИ запрашивает или использует полные профили только выбранных сотрудников.

```text
Кандидаты:
- Анна
- Олег
- Иван
- Мария
```

## Этап 3. Формирование команды

ИИ сравнивает:

- кто будет владельцем результата;
- кто закрывает техническую часть;
- кто отвечает за качество;
- кто работает с заказчиком;
- кому нужен наставник;
- где требуется резерв.

---

# Пример запроса

```md
Проанализируй новую задачу по матрице компетенций и кратким карточкам 21 сотрудника.

Сначала:

1. Отбери сотрудников, которые соответствуют обязательным hard skills.
2. Исключи тех, у кого недостаточно свободных часов.
3. Оцени соответствие soft skills.
4. Выбери 5 лучших кандидатов.
5. Укажи, чьи полные профили нужно дополнительно изучить.
6. Не формируй окончательную команду только по одной технической компетенции.

После анализа выведи:

- топ-5 кандидатов;
- оценку соответствия от 0 до 100;
- причины выбора;
- основные риски;
- недостающие компетенции;
- рекомендуемый состав команды.
```

После получения кандидатов:

```md
Теперь подробно проанализируй полные профили Анны, Олега, Ивана и Марии.

Собери команду для задачи:
[описание задачи]

Укажи:

- владельца результата;
- технических исполнителей;
- специалиста по качеству;
- специалиста по коммуникации;
- резервного сотрудника;
- зоны ответственности;
- загрузку каждого;
- контрольные точки;
- риски;
- формат постановки задачи каждому участнику.
```

---

# Что обязательно добавить в анкету

Для планирования особенно важны не только навыки, но и следующие поля:

```md
- Свободная ёмкость в часах
- Текущая загрузка
- Минимальный комфортный размер задачи
- Возможность работать с клиентом
- Готовность к срочным задачам
- Переносимость неопределённости
- Предпочтительный уровень контроля
- Предпочтительный формат коммуникации
- Типы задач, которые сотрудник выполняет лучше всего
- Типы задач, которые нежелательно назначать
- Дата последнего обновления профиля
```

---

# Что лучше не делать

Не стоит писать в анкете длинные субъективные характеристики:

```text
Плохо:
"Анна немного сложный человек, не очень любит перемены."

Лучше:
"При частом изменении приоритетов работает менее эффективно. Перед сменой направления желательно письменно зафиксировать новую задачу, срок и причину изменения."
```

Также не стоит делать выводы о медицинских или личностных особенностях сотрудника. Для работы достаточно описывать **наблюдаемое рабочее поведение**.

---

# Итоговая рекомендация

Для 21 сотрудника лучше использовать:

1. **одну общую таблицу компетенций**;
2. **21 краткую карточку по 150–400 слов**;
3. **21 полную анкету**, которые подключаются только при необходимости;
4. автоматический первичный отбор кандидатов;
5. подробный анализ только 3–5 подходящих сотрудников.

Такой вариант будет удобнее, дешевле и точнее, чем передавать ИИ все подробные анкеты при каждом планировании.
