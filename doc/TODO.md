Я бы назвал основной режим приложения «Планировщик команды», а текущие «Ролевой мозговой штурм» и «Битва моделей» оставил бы как дополнительные режимы анализа.

### 1. Руководитель вводит задачу

Например:

> Создать MVP веб-сервиса для автоматизации продаж за 8 недель. В команде 4 человека. Бюджет ограничен. Нужно выпустить рабочую версию и провести первые пользовательские тесты.

Дополнительно:

- желаемый результат;
- дедлайн;
- бюджет;
- ограничения;
- приоритет;
- количество часов в неделю;
- обязательные технологии;
- возможные риски.

### 2. Руководитель добавляет специалистов

Например:

```json
{
  "id": "employee_1",
  "name": "Анна",
  "role": "Backend-разработчик",
  "hard_skills": {
    "Python": 5,
    "FastAPI": 5,
    "PostgreSQL": 4,
    "Docker": 3
  },
  "soft_skills": {
    "Коммуникация": 4,
    "Ответственность": 5,
    "Презентации": 2
  },
  "weaknesses": [
    "Недостаточный опыт публичных выступлений"
  ],
  "experience_years": 4,
  "capacity_hours_per_week": 30
}
```

Важно хранить не только навыки, но и:

- текущую загрузку;
- доступность;
- опыт в похожих проектах;
- предпочтения;
- часовой пояс;
- уровень самостоятельности;
- заинтересованность в задаче.

Без информации о загрузке система сможет подобрать подходящего специалиста, но не поймёт, способен ли он реально выполнить работу в заданный срок.

## Какой результат должен выдавать сервис

Например:

### Рекомендуемая структура проекта

| Задача | Исполнитель | Резервный исполнитель | Оценка | Обоснование |
|---|---|---|---:|---|
| Проектирование API | Анна | Сергей | 91% | Сильный Python и FastAPI |
| Интерфейс приложения | Сергей | Ольга | 87% | Опыт React и UI-разработки |
| Тестирование | Ольга | Анна | 82% | Внимательность и опыт QA |
| Пользовательские интервью | Дмитрий | Ольга | 78% | Сильная коммуникация |

Дополнительно система должна возвращать:

1. **Разбиение работы на этапы**
2. **Назначенных специалистов**
3. **Оценку соответствия**
4. **Ожидаемую длительность**
5. **Загрузку каждого человека**
6. **Слабые места плана**
7. **Недостающие навыки**
8. **Риски**
9. **Резервных исполнителей**
10. **План развития слабых навыков**
11. **Необходимые уточняющие вопросы**
12. **Несколько вариантов состава команды**

Например:

> У команды есть сильная техническая база, однако нет специалиста с опытом пользовательских исследований. Если интервью обязательны, рекомендуется привлечь внешнего UX-исследователя или назначить Дмитрия с дополнительной подготовкой.

## Как лучше использовать текущий LLM Council

Я бы не поручал языковой модели полностью решать, кого назначать на работу. Это может привести к субъективным и нестабильным решениям.

Лучше разделить систему на две части.

### 1. Обычный алгоритм

Backend выполняет объективную оценку:

- соответствие hard skills;
- соответствие soft skills;
- опыт;
- доступное время;
- текущую загрузку;
- наличие критичных слабых сторон;
- соблюдение дедлайна.

Пример формулы:

```text
Итоговая оценка =
  45% соответствие hard skills +
  20% соответствие soft skills +
  15% похожий опыт +
  10% доступность +
  10% предпочтения и мотивация
  - штраф за критические риски
```

Коэффициенты должны быть настраиваемыми.

### 2. LLM Council

Совет моделей можно использовать для:

- анализа исходной идеи;
- декомпозиции проекта;
- поиска неучтённых задач;
- проверки назначений;
- анализа рисков;
- подготовки понятного объяснения для руководителя;
- сравнения нескольких вариантов плана.

То есть LLM предлагает и критикует, а backend проверяет ограничения и загрузку.

## Новая логика этапов

Вместо текущих этапов:

```text
Индивидуальные ответы
Взаимные рейтинги
Итоговый ответ
```

для нового режима лучше сделать:

### Этап 1. Анализ задачи

Совет определяет:

- цель;
- ожидаемый результат;
- необходимые этапы;
- подзадачи;
- требования к навыкам;
- предварительные сроки;
- зависимости.

### Этап 2. Подбор команды

Алгоритм сопоставляет задачи со специалистами:

- основной исполнитель;
- резервный исполнитель;
- оценка соответствия;
- ожидаемая нагрузка;
- конфликты;
- пробелы в компетенциях.

### Этап 3. Проверка плана

Роли из `roles.json` анализируют готовое распределение:

- **Практик** — реально ли выполнить план;
- **Аналитик** — как измерить результат;
- **Перфекционист** — какие детали пропущены;
- **Риск-менеджер** — юридические и финансовые риски;
- **Голос клиента** — принесёт ли результат пользу пользователю;
- **Дипломат** — как сбалансировать противоречия.

### Этап 4. Итоговый план

Председатель формирует понятный результат:

- что делать;
- кто делает;
- в какие сроки;
- почему выбран именно этот человек;
- какие есть риски;
- что нужно уточнить.

## Предлагаемая структура backend

Можно добавить следующие файлы:


## Изменения во frontend

Вместо того чтобы вводить всё одним сообщением, лучше добавить отдельный режим:

```text
Планирование команды
Мозговой штурм
Битва моделей
```

Для режима планирования нужен компонент `PlannerForm.jsx`:

- поле «Идея или задача»;
- цель;
- дедлайн;
- ограничения;
- список специалистов;
- добавление hard skills;
- добавление soft skills;
- сильные стороны;
- слабые стороны;
- доступность;
- текущая загрузка.

После расчёта нужен компонент `PlanView.jsx`, который показывает:

- этапы проекта;
- задачи;
- назначенных сотрудников;
- процент соответствия;
- загрузку;
- риски;
- пробелы в навыках;
- альтернативный вариант распределения.

Существующий SSE-механизм можно переиспользовать. Например, добавить события:

```text
plan_start
requirements_complete
tasks_complete
assignments_complete
review_complete
plan_complete
```

## Что нужно исправить в текущем коде до расширения

Есть несколько важных технических моментов:

1. `query_models_parallel()` фактически выполняет запросы последовательно. Там нужно использовать `asyncio.gather()`.
2. В `openrouter.py` отключена проверка SSL-сертификатов. Для production это небезопасно.
3. В `stage3_synthesize_final()` роли частично захардкожены и не соответствуют текущему `roles.json`, где ролей уже 12.
4. `roles.json` и `roles-all.json` дублируют друг друга — лучше оставить один источник.
5. Ответы LLM сейчас возвращаются обычным текстом. Для декомпозиции и распределения лучше использовать строгий JSON с валидацией Pydantic.
6. JSON-файлы в `storage.py` подходят для прототипа, но для нескольких пользователей и одновременной работы лучше использовать SQLite или PostgreSQL.
7. Данные о слабых сторонах сотрудников являются чувствительными. Нужны авторизация, права доступа и ограничение видимости этих данных.

## Какой MVP я бы сделал первым

Минимальная первая версия:

1. Руководитель вводит идею и дедлайн.
2. Добавляет 3–10 специалистов.
3. Для каждого указывает навыки от 1 до 5.
4. Система через LLM разбивает идею на задачи.
5. Backend рассчитывает соответствие специалистов задачам.
6. Система показывает:
   - кто за что отвечает;
   - почему он выбран;
   - сколько времени потребуется;
   - какие есть риски;
   - каких навыков не хватает.
7. Руководитель может вручную изменить назначение и пересчитать план.

Я бы назвал основной режим приложения **«Планировщик команды»**, а текущие «Ролевой мозговой штурм» и «Битва моделей» оставил бы как дополнительные режимы анализа.

Главный принцип продукта:

> **ИИ не просто выбирает людей, а объясняет решение, показывает ограничения и позволяет руководителю принять окончательное решение.**
